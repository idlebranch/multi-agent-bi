# 性能压测记录

> 以下数据采集于项目迁移到 PostgreSQL 之前的 SQLite 阶段，用于确定并发上限和优化方向。当前 runtime 已切换为 PostgreSQL，最新的并发与延迟数据见 README 的「可靠性」一节。

## 一、优化前基线

> 本节保留优化前的问题证据，优化后的复测结果见下一节。

测试日期：2026-07-17
环境：Windows 11、Python 3.12.11、24 个逻辑处理器、130,359,296 字节 SQLite
生产限制：SQL 5 秒超时、最多 200 行、Agent 最多 12 次迭代、LLM 单调用 60 秒超时

### 结论

- 简单问题真实 Agent：并发 8 仍为 8/8；并发 10 首次出现失败；并发 16 仅 10/16。
- 高难度问题单并发：流程完成 8/12，语义正确 6/12，P50 8.23 秒，P95 21.18 秒。
- 数据库重查询：并发 1 的一轮为 24/24，但最慢查询已在 5 秒边缘；并发 2 降为 18/24，并发 64 仅 21/128。
- DeepSeek 在最高 16 并发下没有观察到限流或网络错误；并发失败全部来自 SQLite 查询超时。
- LLM 初始化造成约 40-55 MB 的一次性内存增长，后续压力级别未观察到持续线性增长。

### 高难度语义失败

1. **指标路由丢失维度**：州配送率被固定路由到单行 `delivery_kpis`，无法按客户州分组。
2. **指标路由丢失关联表**：客户州与卖家州组合被固定路由到 `product_sales`，Writer 看不到 `customers`。
3. **语义视图权限过严**：客户 GMV P99 正确使用 `customer_order_summary`，却被确定性规则以“仅供复购”拒绝。
4. **时间粒度选表错误**：年度类别冠军选择了不含日期的类别汇总视图，随后产生无连接键 JOIN。
5. **窗口函数审核漏检**：环比 SQL 在计算 `LAG` 的同一层过滤月份，导致上一月不可见并返回 NULL。
6. **NULL 口径审核漏检**：配送与评价对比没有排除 `delivered_on_time IS NULL`，把未知配送结果算成超时，多出 8 个订单。

### 其他流程问题

- SQL 执行超时会路由回 Writer，重新调用 LLM 生成基本相同的 SQL，再次压垮数据库；资源饱和不应作为 SQL 语义错误处理。
- Reviewer 判断“当前表不可回答”后，流程仍只重试 Writer，不会返回 Catalog 重新选表。
- 配置上限为 12 次迭代，但资源超时案例最终状态显示 iteration=13，限制边界存在一位偏差。
- 四个所谓汇总“视图”是普通 SQLite View，并未物化；每次查询仍会执行底层 JOIN/GROUP BY，这是并发快速退化的主要原因。

### 优先优化顺序

1. 将高频汇总 View 改为可刷新物化表，或迁移到 DuckDB/PostgreSQL，并建立时间、状态、客户和卖家组合索引。
2. 在执行层增加并发信号量、请求队列和背压；当前建议安全并发上限为 4，最多不超过 8。
3. 将查询超时分类为资源错误：禁止回 Writer 重写，改为排队、有限执行重试或返回服务繁忙。
4. 把“视图独占指标”改为“能力/粒度匹配”，根据请求维度检查列是否齐全，并允许 Catalog 补表。
5. Reviewer 增加窗口阶段、NULL 分母/分组、请求维度覆盖的确定性检查；不可回答时路由回 Catalog。

原始数据见 `performance_db_extreme.json`、`performance_db_threshold.json`、`performance_live_advanced_baseline.json`、`performance_live_concurrency_extreme.json` 和 `performance_live_threshold.json`。

## 二、优化后复测

测试日期：2026-07-17
环境：Windows 11、Python 3.12.11、24 个逻辑处理器
数据库：Olist SQLite，242,651,136 字节（约 243 MB）
生产限制：SQL 查询 5 秒、数据库执行并发 4、排队 10 秒、最多返回 200 行、Agent 最多 12 次节点迭代

### 最终结论

- 真实 DeepSeek 高难度端到端测试由工作流 8/12、语义 6/12 提升到工作流 12/12、语义 12/12。
- 简单问题 Agent 并发 16 由 10/16 提升到 16/16，成功吞吐由 0.458 提升到 2.835 请求/秒，P95 由 21.847 秒降到 5.637 秒。
- Agent 突发并发 32 为 32/32，P95 11.559 秒；吞吐没有继续提升，因此不建议作为常规并发。
- 数据库并发 16 由 5/32 提升到 32/32；并发 32 由 11/64 提升到 64/64。
- 并发 64 时为 100/128。其余 28 个请求由 10 秒排队背压明确拒绝，不再表现为 SQLite 查询互相争抢后集体超时。

### 已实施的优化

1. 将七个运行时语义视图改为构建期物化语义表，并为日期、状态、商品、品类、卖家州、客户州及常用组合建立索引。
2. 数据库执行器加入有界并发和排队背压，区分 `queue_timeout`、`query_timeout`、`invalid_sql` 与数据库错误。
3. 容量超时直接结束当前请求，不再浪费 SQL Writer 重试；缺少维度时允许回到 Catalog 重新选表一次。
4. 扩充确定性指标规则，约束时间粒度、状态口径、百分比尺度、窗口函数过滤位置、P99 算法、配送未知值和类别客单价公式。
5. Reviewer 的结构化输出失败会在节点内重试；模型意见与已登记业务口径冲突时，由确定性规则复核。
6. 测试工具增加阶梯并发、P50/P95/P99、吞吐、内存、结构化错误和业务结果断言。

空间代价是 SQLite 从约 130 MB 增至约 243 MB。这是有意的空间换时间：高级标准 SQL 的单轮总执行时间已从约 25.7 秒降至约 2.9 秒。

### 运行建议

- 常规上限：16 个并发 Agent 请求。
- 短时突发：最多 32；此时 P95 已上升到约 11.6 秒，且吞吐低于并发 16。
- 数据库执行并发：保持 4；不要直接跟随 Agent 并发提高。
- 排队上限：保持 10 秒。出现 `queue_timeout` 时应由 API 网关限流或稍后重试，不应让 Writer 改写 SQL。
- 上线到多进程或多实例后，当前进程内信号量无法形成全局限流，应改用网关、Redis 信号量或数据库连接池的全局容量控制。
- 明细进入千万至亿级后，保留现有 Agent、指标定义和测试契约，将执行适配器迁移到 DuckDB、PostgreSQL 或云数仓。
