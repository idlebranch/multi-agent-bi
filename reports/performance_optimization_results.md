# Multi-Agent BI 性能优化复测报告

测试日期：2026-07-17
环境：Windows 11、Python 3.12.11、24 个逻辑处理器
数据库：Olist SQLite，242,651,136 字节（约 243 MB）
生产限制：SQL 查询 5 秒、数据库执行并发 4、排队 10 秒、最多返回 200 行、Agent 最多 12 次节点迭代

## 最终结论

- 真实 DeepSeek 高难度端到端测试由工作流 8/12、语义 6/12 提升到工作流 12/12、语义 12/12。
- 简单问题 Agent 并发 16 由 10/16 提升到 16/16，成功吞吐由 0.458 提升到 2.835 请求/秒，P95 由 21.847 秒降到 5.637 秒。
- Agent 突发并发 32 为 32/32，P95 11.559 秒；吞吐没有继续提升，因此不建议作为常规并发。
- 数据库并发 16 由 5/32 提升到 32/32；并发 32 由 11/64 提升到 64/64。
- 并发 64 时为 100/128。其余 28 个请求由 10 秒排队背压明确拒绝，不再表现为 SQLite 查询互相争抢后集体超时。

## 已实施的优化

1. 将七个运行时语义视图改为构建期物化语义表，并为日期、状态、商品、品类、卖家州、客户州及常用组合建立索引。
2. 数据库执行器加入有界并发和排队背压，区分 `queue_timeout`、`query_timeout`、`invalid_sql` 与数据库错误。
3. 容量超时直接结束当前请求，不再浪费 SQL Writer 重试；缺少维度时允许回到 Catalog 重新选表一次。
4. 扩充确定性指标规则，约束时间粒度、状态口径、百分比尺度、窗口函数过滤位置、P99 算法、配送未知值和类别客单价公式。
5. Reviewer 的结构化输出失败会在节点内重试；模型意见与已登记业务口径冲突时，由确定性规则复核。
6. 测试工具增加阶梯并发、P50/P95/P99、吞吐、内存、结构化错误和业务结果断言。

空间代价是 SQLite 从约 130 MB 增至约 243 MB。这是有意的空间换时间：高级标准 SQL 的单轮总执行时间已从约 25.7 秒降至约 2.9 秒。

## 运行建议

- 常规上限：16 个并发 Agent 请求。
- 短时突发：最多 32；此时 P95 已上升到约 11.6 秒，且吞吐低于并发 16。
- 数据库执行并发：保持 4；不要直接跟随 Agent 并发提高。
- 排队上限：保持 10 秒。出现 `queue_timeout` 时应由 API 网关限流或稍后重试，不应让 Writer 改写 SQL。
- 上线到多进程或多实例后，当前进程内信号量无法形成全局限流，应改用网关、Redis 信号量或数据库连接池的全局容量控制。
- 明细进入千万至亿级后，保留现有 Agent、指标定义和测试契约，将执行适配器迁移到 DuckDB、PostgreSQL 或云数仓。
